# Core files changed for the Feedback module

The core rebuild (stages 1–3) had no module extension points: no registry, no `modulesOff`, no Features page, no AI tools' endpoint. It did already place a `feedback` menu row behind a `feedbackOn` option (stage 3's navigation conformance asks for it), and it held a stub `/feedback` page of its own. **3 core files changed, 1 core file added, 1 folder created.** That the core needed changing for a first module is itself a finding (GAPS F1–F3).

| File | Change | Why |
|---|---|---|
| `app/modules.mjs` (new) | The extension points: `loadModules` (each `modules/<id>/index.mjs` exports `register(core)`), `isOn(W, id)` over `Workspace.modulesOff`, the page's and the tools' switched-off sentences, Features' groups. | Stage 5's entry criteria assume the core "keeps a workspace's switched-off modules and refuses a switched-off module's actions and AI tools"; the core rebuild had none of it. |
| `app/server.mjs` | (1) Loads the modules and gives them a small core API (W, layout, esc, send, redirect, isAdmin, nameOf, person, What's new entries). (2) Dispatches to a module's own addresses before the core's; while it is off, a GET of its addresses is Page not found with "{Module} is switched off in {workspace}. An admin can switch it on in Workspace, Features." and a POST to them is refused with the module's sentence ("Feedback is off in {workspace}."). (3) `ctx.feedbackOn`, `ctx.moduleScripts`, `ctx.menuBadges`, `ctx.host`, `ctx.referrer` from the modules that are on. (4) `/workspace/features` (GET: groups, a tick box per module, the third line, Undo; POST: admins only, sets `W.modulesOff`, logs “switched Feedback off” in Activity). (5) `/api/mcp`: JSON-RPC `tools/list` and `tools/call` over every module's tools; a switched-off module's tool answers "{Module} is switched off in {workspace}, so {tool} can’t be used there. An admin can switch it on in Workspace, under Features."; `GET /api/mcp?check`. The token stands for its person (`Authorization: Bearer <person id>`), since AI access (stage 4) isn't built. (6) Help: a module's articles take its ids (`feedback`, `inbox`) and leave Help while it is off. (7) `/whats-new` renders its entries and asks each module for a note ("You raised this"). (8) `/more` passes `feedbackOn` (it showed Feedback whatever the switch). (9) Removed the core's own `/feedback` stub page and its POST: they belong to the module. (10) The referrer kept for "Mark up the last screen" skips `/feedback` and `/more`. | Each is an extension point the module registers into, or a core place (Features, the AI tools' endpoint, Help, What's new) the kit says the core owns. |
| `app/lib.mjs` (`layout`) | A module's plain-text badge beside its menu row (“75 new”), and its scripts on every page while it is on. | INBOX-TRIAGE: the New count beside the row; MARKUP: Ctrl+Shift+M from anywhere. |
| `local/` (folder) | Created, empty. | `s1.mjs` writes stage 1's scratch CSVs under `rebuild/local/`, which wasn't in the copy handed to this session: the app wouldn't start without it. |

Not changed: `stage3.mjs` (its `menuGroups`, `litItem` and `pageName` already took `feedbackOn`), `main.mjs`, `engine.mjs`, `store.mjs`. The drill still scores 100% with the module in, and with its folder removed (the core then has no Feedback row, no page and no tools).
