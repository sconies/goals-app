# Working on this repository

- **What Faro is for (Lane, 8 Nov):** a model for an internal application to copy, plus demos and an off-site. It never holds real company data. Build what the rebuild should copy (product ideas, rules, screen patterns); write what the internal platform provides anyway (sign-in, single sign-on, scale, backups, observability) into the spec as requirements instead. See `docs/backlog.md`.
- **Design:** read `docs/design-rules.md` before changing anything visual. It must not look like a default AI interface. In particular:
  - no coloured edge stripes on cards, rows or tiles;
  - no quote bars;
  - no emoji icons;
  - no pastel pill badges.

  Status is always a shape plus a word. `npm run evals` enforces these rules (design check P6).
- **Quality gate:** nothing is pushed until `npm run typecheck`, `npm test` and `npm run evals:changed` pass locally: the smoke gate plus every journey and F/N/P check the changed files touch (`evals/touches.cjs`; it runs the full suite by itself when a change touches shared code). Single checks still run with `FINISH=…` or `ONLY=…`. PR CI runs `npm run evals:pr`: the core journeys plus every journey and check the PR's files touch, but never the whole suite (a change to shared code gets the full suite after the merge); when that is more than 25 journeys beyond the core ones, only the 25 the PR's files name most directly run, and the rest wait for the full suite after the merge, so the job stays inside its 30 minutes (Lane, 14 Nov; `evals/touches.cjs` `capJourneys`). The runs before a merge (`evals:changed`, `evals:pr`, `evals:smoke`) run phone-sized pages with the CPU slowed 4×, one journey process after another (`evals/phoneCpu.cjs`, Lane, 13 Nov), so a race only a slow phone shows turns up before the merge; desktop pages, and the full suite after the merge, run at full speed. Never raise a budget to pass under it; ask planning if a limit truly needs to change. The full suite (`npm run evals`) runs in parallel shards on main after merge; a failure comments on one rolling "Full evals failing on main" issue (opening it if none is open), which is fixed or reverted straight away; the next green run closes it. Run the full `npm run evals` locally when changing shared layout, styles or the eval harness itself. New features come with their own evals.
- **Rebuild kit (Lane, 7 Nov; in force since 8k):** every item also adds its module's section of `spec/`, its conformance rows and its rebuild stage (`rebuild` in its `module.json`, which `npm run spec` turns into a page in `spec/rebuild/`), and runs that stage's drill where it has one: a fresh session that sees only `spec/` and `llms.txt` rebuilds the stage and scores it (`spec/rebuild/README.md`). CI fails a module with no stage (`scripts/check-rebuild.mjs`) and a harness that no longer scores Faro's own rules at 100% (`npm run drill -- scripts/drill-faro`). An item isn't done without them.
- **Help and What's new:** every change people can see updates the guide in `src/help/guide.ts` (an article per screen; new screens, routes and requirements need one, checked by `src/help/guide.test.ts`). **What's new is for features only (Lane, 13 Nov):** a new feature, or a visible change to how one works, adds an entry at the top of `src/help/whatsNew.ts`; bug fixes, review fixes, polish, wording and refactors don't, unless the fix is major (it changes a number people rely on, restores something that was broken for many, or changes who may do what). CI fails a pull request that changes `src/` or `supabase/migrations` without touching What's new; a PR with no feature in it says `[no news]` in a commit message.
- **Docs follow the build (Lane, 13 Nov):** a PR that adds or changes a module, a route, a rule or an MCP tool also updates the lines about it in `README.md`, `docs/architecture.md` and `docs/handoff.md`; the README's feature list follows `docs/architecture/module-map.md`. In-app Help, What's new and the generated spec are already enforced by tests; these hand-written pages are not, so keep them true as you go.
- **Language:** plain British English. The UI is low density and calm, with one primary action per screen.
- **Rules live once:** status rules, check-in rules and the bulk-change engine are shared by the app, the import and the MCP server. Don't restate them.
- **Database:** migrations live in `supabase/migrations`. A paste-in script for the ones not yet applied lives in `supabase/manual`. CI applies migrations beside the deploy, in no order with it, so a release that needs a migration ships it one merge ahead of the code that uses it (AX10). Since 0035 (backlog 0c) Faro lives in its own schema, `faro`, and migrations are written differently; read `supabase/README.md` first:
  - from 0036 on they run as `faro_owner` with `search_path` faro: plain names land in `faro`, never `public`;
  - a new table or function gets none of Supabase's default grants there: write every grant out (`grant select, insert … to anon`), and revoke a new function from `public` unless everyone may run it;
  - a new table or column gets no redirect in `public` (0035's are fixed `select *` views): the app sees it only once the Data API offers `faro`, so that setting comes first; changing a column a redirect shows fails until the redirects go (0c2);
  - nothing reaches outside `faro` (no `auth.`, `storage.` or `cron.`): the role can't, and the fence check fails if anything in `faro` belongs to another role.
- **MCP:** after changing `server/` or anything it imports, run `npm run build:mcp` and commit `api/mcp.js`.
- **The spec (8a, 8b):** `spec/` and `llms.txt` are generated from the code. After changing a rule, a type, a screen, a test title, a requirement, a journey, a module.json or the demo workspace, run `npm run spec` and commit what it writes; `npm test` and CI fail while it is out of date. A rule's words and worked examples live in `src/spec/rules.ts`, a screen's main action in `src/spec/screens.ts`. Never edit `spec/` by hand.
- **Architecture:** a modular monolith (`docs/architecture.md`). Build new features as modules that register into the core's extension points; keep `src/domain` free of database, screen and network code; no microservices.
- **Every distinct feature behind a switch (Lane, 13 Nov):** each distinct, self-contained feature is a module with its own feature switch (Workspace → Features), so a workspace can turn it off and the core works without it. CI's "core journeys without <module>" checks prove it. With the switch off: no menu row, no Home card, no MCP tool answers (they refuse with the module-off sentence), and the import says once what it didn't read. A feature that can't be switched off must say why in its spec.
- **Modular for the handoff (Lane, 13 Nov):** the handoff must show the internal team they can build Faro module by module: the core first, then each module on its own, each with its spec section, conformance rows, rebuild stage and switch. `docs/handoff.md` and the rebuild kit say this plainly, and the full drill (item 11) rebuilds the core and then adds modules one at a time.
- **Ideas go to the backlog, not straight into code (Lane, 7 Nov):** when Lane shares an idea, a request or something he spotted, don't start building it. Add it to `docs/backlog.md`, place it in the priority order (value, effort, and what it depends on or unblocks), and tell him where it landed. Build only when he picks an item, says "build/do/start it", or it's the next item he has approved. Questions get answered; they don't become work. Bugs that break main or a merged release are the exception: fix those at once.
- **Supabase changes:** CI applies new migrations automatically when a PR merges to main (`scripts/migrate.mjs`, using the `DATABASE_URL` secret, added 7 Nov), so merging is the approval. Put the full SQL in the PR description so Lane sees it before merging, and keep migrations safe to run twice. Hand SQL to Lane only if CI can't apply it; then as plain `.txt` files of at most about 5 KB, split at statement boundaries and tested first.
- **When to ask Lane (7 Nov):**
  - **Decide and tell him after:** backlog wording, and order within the priorities he has set; the details of an item; docs edits; anything easy to undo.
  - **Ask first:** what to build next; merging to main; anything touching live data, or settings only he can change (Supabase, Vercel); product calls where he has given no preference.
  - **How to ask:** one batch of multiple-choice questions, the recommended answer first. Never one at a time.
  - Routine commands can be pre-approved in `.claude/settings.json`. Lane decides what goes there; Claude adds an entry only when he asks for it (13 Nov: `create_session` and `send_message`, so planning starts and messages tracks without an approval each time).
- **When a session hands over (Lane, 14 Nov; replaces the 13 Nov "80%" rule):** every turn re-reads the whole context. Cached reads are cheap per token, but at 500k+ tokens they are most of the bill: on 13 Nov, about $1,430 across 28 sessions, mostly re-reading (track 4 re-read 760M tokens to write 1.2M; the reviewer 664M). A fresh start costs 50–100k tokens to read in. So:
  - **Build sessions** hand over at about **300k tokens of context** (check with `get_session`, `context_usage.used_tokens`), when the list is done, or when they notice they are losing track, whichever comes first. Keep context lean while working: grep instead of reading whole files, and send eval runs and long logs to a subagent that returns only the result.
  - **Mechanical work goes to Sonnet subagents** (`model: "sonnet"`): merging main and resolving What's new, rebuilding `api/mcp.js` and `spec/`, eval runs and reruns, docs edits, watching CI. The build session keeps design, code and review decisions.
  - **The build reviewer** starts fresh every day, or after about 20 PRs, from its log on `build-reviews`.
  - **The planning session** keeps its context small (no PR subscriptions or CI relaying; builds report once) and hands over at about 300k, or after a long run, by updating `docs/handover/planning.md` (replacing its entry) and giving Lane a ready-to-paste prompt.
  - **At most three build tracks at once** (plus the reviewer). Fewer, longer tracks beat many short ones: give a session a whole area's list, not one item; don't start a new session for a single small fix that a running track can take.
- **How we work (Lane, 7 Nov):** this planning session takes ideas, grills, the backlog and merge decisions; each release is built in its own fresh session started from a short brief that points at its backlog item. Only one build at a time per area. Backlog edits ride with the next feature PR instead of getting their own. While builds and CI run, stay quiet: report only merges, failures and decisions Lane must make. Use the strongest model for planning, architecture and review, and a lighter model for mechanical work (watching CI, docs edits, screenshots, routine eval reruns).
